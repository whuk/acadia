# 기능 개요

서비스별 Circuit Breaker 인스턴스 분리.

현재 `GatewayConfig`는 모든 서비스 라우트(main·public)에 단일 인스턴스 ID `gatewayCircuitBreaker`(`GatewayConfig.kt:27`)를 사용한다. Resilience4j는 ID 기준으로 인스턴스를 관리하므로 전체 게이트웨이에 서킷 브레이커가 하나만 존재하며, 한 백엔드의 장애로 서킷이 열리면 정상인 다른 백엔드로 가는 호출까지 `wait-duration-in-open-state`(60초) 동안 차단된다. 반대로 정상 백엔드의 성공 호출이 공유 sliding window의 실패율을 희석해 장애 감지가 지연되는 문제도 있다.

이를 서비스별 인스턴스 `cb-{service.name}`으로 분리해 백엔드 장애를 서비스 단위로 격리한다.

## 구현 목표

- 백엔드 A의 장애로 서킷이 열려도 백엔드 B로의 라우팅은 정상 동작한다 (장애 격리).
- 같은 서비스의 main 라우트와 public 라우트는 같은 백엔드를 향하므로 하나의 서킷 인스턴스를 공유한다.
- 서킷 브레이커 설정(sliding window, 실패율 임계값 등)은 `resilience4j.circuitbreaker.configs.default`로 이전해, 서비스가 추가돼도 설정 없이 동일 정책이 적용된다 (기존 "yml 항목 추가만으로 서비스 추가" 특성 유지).
- 기존 resilience 테스트 전체가 새 인스턴스 명명 체계에서 계속 통과한다.

## 설계

### 변경 대상

| 파일 | 변경 내용 |
|---|---|
| `config/GatewayConfig.kt` | `CIRCUIT_BREAKER_NAME` 상수 제거(또는 prefix 상수 `CIRCUIT_BREAKER_PREFIX = "cb-"`로 대체). main·public 라우트의 `circuitBreaker { it.setId(...) }`를 `"cb-${service.name}"`으로 변경. 같은 서비스의 두 라우트는 같은 ID를 사용 |
| `src/main/resources/application.yml` | `resilience4j.circuitbreaker.instances.gatewayCircuitBreaker` → `resilience4j.circuitbreaker.configs.default`로 이전. Resilience4j는 미등록 인스턴스를 default config로 lazy 생성하므로 서비스별 개별 항목은 불필요 |
| 기존 테스트 4곳 (`CircuitBreakerTest`, `BackendErrorTest`, `BackendUnavailableTest`, `GatewayErrorFormatTest`) | `@DynamicPropertySource`의 `resilience4j.circuitbreaker.instances.gatewayCircuitBreaker.*` 키를 `resilience4j.circuitbreaker.configs.default.*`로 변경 |
| `README.md`, `docs/phase-4-resilience.md` | 설정 예시를 `configs.default` 기준으로 갱신 |

### 데이터 흐름 (변경 후)

```
요청 → 라우트(service.path 매칭)
     → CircuitBreaker[cb-{service.name}]  ← 서비스별 독립 sliding window
     → Retry → 백엔드(service.url)
```

### 설계 결정

1. **인스턴스 ID 명명**: `cb-{service.name}`. `service.name`은 라우트 ID에도 쓰이는 고유 식별자이므로 충돌 없음.
2. **main/public 라우트 공유**: 두 라우트는 같은 백엔드 프로세스를 호출하므로 장애 신호를 하나의 window에 집계하는 것이 올바르다. 경로별 분리는 같은 백엔드 장애를 이중 감지하게 되어 채택하지 않는다.
3. **`configs.default` 사용**: 서비스별 `instances.cb-{name}` 항목을 yml에 나열하는 방식은 서비스 추가 시 수동 동기화 지점이 생기므로 배제한다. 특정 서비스만 다른 임계값이 필요해지면 그때 `instances.cb-{name}`으로 오버라이드하면 된다 (선제 구현하지 않음 — YAGNI).
4. **테스트 베이스**: 이 프로젝트의 기존 관례(테스트 클래스에 `@SpringBootTest` + `WireMockExtension` + `@DynamicPropertySource` 직접 선언, 예: `CircuitBreakerTest`)를 따른다. 격리 테스트는 WireMock 인스턴스 2개(user-service용, order-service용)를 등록한다.

### 주의점

- Green 단계에서 `GatewayConfig`의 ID를 바꾸는 순간 기존 4개 테스트의 `instances.gatewayCircuitBreaker.*` 프로퍼티가 무효화되어(존재하지 않는 인스턴스 설정) default 설정으로 동작이 바뀐다. 따라서 첫 사이클의 Green에 기존 테스트 프로퍼티 마이그레이션을 반드시 포함한다. 그렇지 않으면 `CircuitBreakerTest`는 window 10/최소 5 기본값으로 4회 호출로는 서킷이 열리지 않아 실패한다.
- 서킷 상태는 ApplicationContext 단위로 유지된다. 격리 테스트에서 서킷을 여는 테스트와 다른 테스트 간 상태 간섭이 없도록, 격리 테스트는 전용 테스트 클래스(전용 컨텍스트)로 작성하고 테스트 간 순서 의존을 만들지 않는다.
