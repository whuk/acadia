argument를 기반으로 작업 계획을 수립하여 프로젝트 루트에 plan.md를 생성한다.

## 사전 검증

1. `$ARGUMENTS`가 비어있으면 다음 메시지를 출력하고 **중단**한다:
   > argument가 비어 있습니다. 구현할 기능 설명 텍스트 또는 PRD 파일 경로를 반드시 입력해 주세요.
   > 예: `/plan PRD2.md` 또는 `/plan 사용자 인증 기능 구현`

2. 프로젝트 루트에 `plan.md`가 이미 존재하는지 확인한다. 존재하면 다음 메시지를 출력하고 **중단**한다:
   > 프로젝트 루트에 plan.md가 이미 존재합니다.
   > `/plan_move`를 실행하여 기존 plan.md를 아카이빙한 후 다시 `/plan` 명령을 실행해 주세요.

## Argument 해석

- `$ARGUMENTS`가 `.md`, `.txt` 등 파일 확장자를 포함하는 경로이면 해당 파일을 Read 도구로 읽어 내용을 파악한다. 파일이 존재하지 않으면 사용자에게 알리고 중단한다.
- 파일 경로가 아닌 일반 텍스트이면 해당 텍스트를 직접 분석한다.

## 코드베이스 탐색

argument 내용을 파악한 뒤, 관련된 코드베이스를 탐색하여 현재 구현 상태, 디렉토리 구조, 기존 패턴 등을 파악한다.

## plan.md 생성

argument 내용 + 코드베이스 분석 결과를 종합하여 프로젝트 루트에 `plan.md`를 Write 도구로 생성한다.

### plan.md 문서 구조

```markdown
# 기능 개요

(argument 내용을 정리한 기능 설명. 무엇을 왜 만드는지 대략적으로 서술한다.)

## 구현 목표

(달성해야 할 핵심 목표를 명확히 정의한다.)

- 목표 1
- 목표 2
- ...

## 설계

(구현에 필요한 핵심 설계 사항을 정리한다. 변경/생성할 주요 클래스, 계층 구조, 데이터 흐름 등을 포함한다.)

## 작업 계획

### Phase 1: (단계 이름)

- [ ] 작업 항목 1
- [ ] 작업 항목 2

### Phase 2: (단계 이름)

- [ ] 작업 항목 3
- [ ] 작업 항목 4

(필요한 만큼 Phase를 추가한다)
```

### 작성 원칙

- 작업 항목은 하나의 논리적 작업 단위로 쪼갠다. 한 항목이 너무 크면 세분화한다.
- 각 작업 항목은 구체적이어야 한다. "구현한다"가 아니라 무엇을 어떻게 하는지 명시한다.
- Phase는 의존성 순서에 따라 배치한다. 선행 작업이 먼저 온다.
- 테스트 작성 항목을 포함한다. TDD 사이클에 따라 테스트가 구현보다 먼저 온다.
- 프로젝트의 .claude/rules/ 에 정의된 규칙(계층 분리, DDD, Service/Finder 분리 등)을 준수하는 설계를 반영한다.

$ARGUMENTS - 필수: 구현할 기능 설명 텍스트 또는 PRD 파일 경로
