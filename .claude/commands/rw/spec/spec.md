# /rw:spec:spec — 기능 명세(spec.md) 생성

사용자가 러프하게 전달한 기능 설명을 질문 라운드로 구체화하여, 프로젝트 루트에 `spec.md`를 생성한다. 이 문서는 "무엇을 왜 만들고 어떻게 동작해야 하는가"를 확정하는 기능 단위 명세이며, `/rw:plan:plan`의 입력이 된다. 구현 방법이 아니라 요구사항을 다룬다.

## 1단계: 사전 검증

1. `$ARGUMENTS`가 비어있으면 다음 메시지를 출력하고 **중단**한다:
   > argument가 비어 있습니다. 명세로 만들 기능을 러프하게라도 설명해 주세요.
   > 예: `/rw:spec:spec 로그인 5회 실패하면 계정 잠금`

2. 프로젝트 루트에 `spec.md`가 이미 존재하는지 확인한다. 존재하면 다음 메시지를 출력하고 **중단**한다:
   > 프로젝트 루트에 spec.md가 이미 존재합니다.
   > `/rw:spec:spec_move`를 실행하여 기존 spec.md를 아카이빙한 후 다시 `/rw:spec:spec` 명령을 실행해 주세요.

## 2단계: 코드베이스 탐색

`$ARGUMENTS`가 가리키는 기능과 관련된 코드베이스를 탐색한다. 현재 구현 상태, 디렉토리 구조, 기존 패턴, 유사 기능의 처리 방식(에러 응답, 검증, 상태 전이 등)을 파악한다. 프로젝트에 `PRD1.md`/`PRD2.md`가 있으면 함께 읽어 용어와 기능명을 맞춘다.

이 단계는 **3단계의 질문을 구체화하기 위한 선행 조건**이다. 기존 구현을 모른 채 일반론적인 질문을 던지지 않기 위함이며, 여기서 이미 답이 확인되는 항목은 질문 대상에서 제외한다.

## 3단계: 질문 라운드

`AskUserQuestion` 도구로 아래 네 라운드를 **순서대로** 진행한다. 한 라운드에 한 번 호출하고, 사용자 답변을 받은 뒤 다음 라운드로 넘어간다.

### 라운드 1 — 목표·범위·비목표

누가 왜 이 기능을 쓰는지, 이번 작업에 포함할 것과 뺄 것은 무엇인지, 기존 동작 중 무엇이 바뀌는지를 확정한다.

### 라운드 2 — 주요 시나리오

정상 흐름을 확정한다. 액터(누가), 트리거(무엇을 하면), 기대 결과(무엇이 일어나는가)를 갖춘 형태로 뽑아낸다. 진입 경로가 여럿인지(화면·API·배치·메시지 등) 함께 확인한다.

### 라운드 3 — 엣지 케이스·실패 시나리오

경계값, 빈 값, 중복 요청, 동시 실행 등 엣지 케이스를 확정한다. 실패했을 때 사용자에게 무엇을 보여주고 시스템 상태를 어떻게 남기는지(롤백 여부, 재시도 가능 여부)도 함께 정한다.

### 라운드 4 — 완료의 정의

무엇이 참이면 이 기능이 끝난 것인지, 각 항목을 어떤 수단(테스트·명령·화면 확인)으로 검증하는지 확정한다.

### 라운드 운영 규칙

- 2단계 탐색 결과를 반영한 **구체적인 선택지**를 제시한다. 기존 코드에서 답이 이미 확인되는 항목은 질문하지 않고 확인만 한다.
- 사용자가 답을 미루면 추측으로 채우지 않는다. 해당 항목을 `spec.md`의 "미해결 질문"에 남기고 다음 라운드로 넘어간다.
- 라운드는 **최대 4회**로 진행하고, 답변에서 새로 드러난 쟁점이 있으면 1회만 추가한다. 그 이상 되묻지 않는다.

## 4단계: spec.md 생성

**Write 직전에 루트 `spec.md`의 존재 여부를 다시 확인한다.** 1단계 검사와 이 시점 사이에는 코드베이스 탐색과 최대 4~5라운드의 질문이 끼어 있어 시간이 오래 걸리며, 그동안 다른 세션이 `spec.md`를 만들었을 수 있다. 그 사이 생겼으면 덮어쓰지 말고 다음을 출력한 뒤 **중단**한다(수집한 답변은 세션에 그대로 출력해 사용자가 잃지 않게 한다):

> 명세를 정리하는 동안 프로젝트 루트에 spec.md가 새로 생겼습니다. 다른 세션이 만들었을 수 있어 덮어쓰지 않고 중단합니다. 내용을 확인한 뒤 필요하면 `/rw:spec:spec_move`로 아카이빙하고 다시 실행해 주세요.

확인이 끝나면 `$ARGUMENTS` + 2단계 탐색 결과 + 3단계 답변을 종합하여 프로젝트 루트에 `spec.md`를 Write 도구로 생성한다.

### spec.md 문서 구조

```markdown
# {기능명} 스펙

(무엇을 왜 만들고 어떻게 동작하는지 1~3문장으로 요약한다. 이 문단만 읽어도 기능의 의도가 파악되어야 한다.)

## 목표

- (이 기능이 달성해야 할 것)

## 범위

- (이번 작업에 포함되는 것)

## 비목표

- (의도적으로 하지 않는 것과 그 이유)

## 주요 시나리오

1. (액터)가 (트리거)하면 (기대 결과)가 발생한다.

## 엣지 케이스

- (경계 조건) → (기대 동작)

## 실패 시나리오

- (실패 조건) → (사용자에게 보이는 것 / 시스템에 남는 상태)

## 완료의 정의

- [ ] (참·거짓으로 판정 가능한 검증 항목)

## 미해결 질문

- (아직 확정하지 못한 것과, 언제까지 정해야 하는지)
```

### 작성 원칙

- **완료의 정의는 검증 가능해야 한다.** 각 항목이 테스트나 명령 하나로 참·거짓 판정 가능한 문장이어야 한다. `/rw:plan:plan`이 이 항목들을 Phase별 테스트 체크리스트로 변환하는 전제다.
- 시나리오는 액터·트리거·기대 결과를 갖춘 문장으로 쓴다. "잘 동작한다", "적절히 처리한다" 같은 판정 불가 서술을 쓰지 않는다.
- **구현 방법을 명세에 넣지 않는다.** 클래스명, 계층 배치, 라이브러리 선택은 `plan.md`의 설계 섹션 몫이다. 이 문서는 "무엇을"과 "왜"만 다룬다.
- 비목표는 "안 한다"만 적지 않고 왜 빼는지를 함께 적는다. 나중에 범위가 흔들릴 때 판단 근거가 된다.
- 미해결 질문이 없으면 섹션에 "없음"이라고 적는다. 섹션 자체를 삭제하지 않는다.
- 한글로 작성하고 기술 문서 톤을 유지한다. 이모지를 사용하지 않는다.

## 결과 보고

- 생성된 파일 경로(`spec.md`)
- 기능 요약(1~2문장)
- 시나리오 수, 엣지 케이스 수, 완료 정의 항목 수
- 미해결 질문이 남아 있으면 그 목록
- 다음 단계 안내(`/rw:plan:plan`을 인자 없이 실행하면 이 `spec.md`로 계획을 세운다)

## 하지 말아야 할 것

- argument가 비어 있는데 임의로 진행하기 (사전 검증에서 반드시 중단)
- 프로젝트 루트에 spec.md가 이미 존재하는데 덮어쓰기 (`/rw:spec:spec_move`로 먼저 아카이빙 안내)
- 1단계 검사만 믿고 Write 직전 재확인을 건너뛰기 (질문 라운드 중 다른 세션이 만든 spec.md를 덮어쓰게 된다)
- 재확인에 걸려 중단하면서 수집한 답변을 버리기 (세션에 출력해 사용자가 다시 답하지 않게 한다)
- 코드베이스 탐색 없이 곧바로 질문 라운드를 시작하기 (2단계 참조)
- 사용자가 답하지 않은 항목을 추측으로 채우기 (미해결 질문에 남긴다)
- 라운드 상한을 넘겨 계속 되묻기
- 클래스·계층·라이브러리 등 구현 방법을 명세에 적기 (`plan.md`의 몫)
- 판정 불가능한 서술("잘 동작한다")을 완료의 정의에 적기
- 이모지 사용하기
