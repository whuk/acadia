# /rw:git:branch — 작업 브랜치 생성

현재 작업에 맞는 새 브랜치를 생성합니다. 프로젝트 루트의 `plan.md` 존재 여부에 따라 분기합니다.

## 1단계: 분기 판정

프로젝트 루트에 `plan.md`가 존재하는지 확인하세요.

- 존재 → **경로 A**로 진행
- 부재 → **경로 B**로 진행

## 2단계: 대상 텍스트 결정

### 경로 A: plan.md 기반 (TDD 사이클)

1. `plan.md`를 읽고 **`- [ ]`(미완료)인 항목 중 첫 번째** **하나**를 찾으세요. `- [x]`(완료)와 `- [~]`(다른 세션이 `/rw:tdd:go`로 진행 중)는 건너뜁니다 — `[~]` 항목으로 브랜치를 만들면 다른 세션과 같은 작업을 하게 됩니다.
2. 대상이 하나도 없으면 다음 메시지를 출력하고 **중단**하세요:
   > plan.md에 착수할 수 있는 미완료 테스트가 없습니다. 남은 항목이 모두 완료(`[x]`)이거나 다른 세션이 진행 중(`[~]`)입니다. 새 계획을 작성하거나 작업할 변경사항을 만든 뒤 다시 실행해 주세요.
3. 그 테스트 설명을 **대상 텍스트**로 삼아 3단계로 진행하세요.

### 경로 B: 현재 변경사항 기반

1. 다음 명령으로 작업 디렉토리 상태를 수집하세요:
   - `git status --short` — 변경/신규/삭제 파일 목록
   - `git diff --stat HEAD` — 스테이징 + 비스테이징 변경 요약
   - 변경 파일이 적거나 의도가 모호하면 `git diff HEAD` 또는 Read로 내용을 확인
2. 변경사항이 전혀 없으면(clean working tree) 다음 메시지를 출력하고 **중단**하세요:
   > plan.md도 없고 작업 디렉토리에 변경사항도 없습니다. 먼저 작업할 내용을 만들거나 `/rw:plan:plan`으로 계획을 작성해 주세요.
3. 변경된 파일 경로와 내용을 종합해 작업 의도를 한 줄로 요약하세요. 이 요약을 **대상 텍스트**로 삼아 3단계로 진행하세요.

## 3단계: 브랜치 유형 결정

대상 텍스트를 분석하여 다음 중 하나의 유형을 선택하세요:

- `feature/` : 새로운 기능 구현
- `fix/` : 버그 수정, 결함 수정
- `refactor/` : 리팩터링, 구조 개선 (동작 변경 없음)
- `test/` : 테스트 추가/수정만 해당
- `chore/` : 설정, 문서, 빌드 등 기타 작업

**경로 B 전용 휴리스틱** (대상 텍스트 분석이 모호할 때 파일 패턴으로 보조 판정):

- 테스트 디렉토리(`src/test/`, `*Test.kt`, `*Spec.kt`, `*.test.*`)만 변경 → `test/`
- `.github/`, `gradle/`, `build.gradle*`, `pom.xml`, `*.md`, `.gitignore`, 설정 파일만 변경 → `chore/`
- production 소스가 포함된 경우 변경 내용으로 판단:
  - 새 파일·신규 메서드 추가 위주 → `feature/`
  - 기존 로직 보정·예외 처리·검증 추가 위주 → `fix/`
  - 이름 변경·이동·메서드 추출 등 동작 변경 없는 정리 위주 → `refactor/`
- 끝까지 모호하면 `feature/`를 기본으로 사용

## 4단계: 브랜치명 생성

대상 텍스트를 기반으로 간결한 브랜치명을 생성하세요:

- 영어 소문자 사용, 단어 구분은 하이픈(`-`)
- 예: `feature/add-user-login`, `fix/null-pointer-in-parser`, `chore/update-readme`

## 5단계: 브랜치 생성

1. 현재 브랜치 상태를 확인하세요 (`git status` / `git branch --show-current`).
2. **분기 기점을 확인하세요.** `git checkout -b`는 현재 HEAD에서 갈라지므로, 이전 작업 브랜치에 머물러 있으면 새 브랜치가 그 위에 쌓입니다. 앞 브랜치가 머지되면서 삭제되면 그 위에 쌓인 커밋이 붕 뜹니다.
   - 현재 브랜치가 기본 브랜치(`git remote show {remote}`의 HEAD 브랜치)면 그대로 3항으로 진행합니다.
   - 다른 브랜치에 있으면 사용자에게 알리고 확인받습니다. 임의로 checkout 하지 마세요:
     - 현재 브랜치 위에 쌓는다 (앞 작업에 이어지는 후속 작업일 때)
     - 기본 브랜치로 이동한 뒤 분기한다 (독립적인 새 작업일 때). 워킹트리에 변경사항이 있으면 그 변경이 함께 딸려간다는 점을 함께 알립니다
3. `git checkout -b <브랜치명>`으로 브랜치를 생성하세요.
4. 이름 충돌은 **사전 조회가 아니라 명령의 실패로 판정**하세요. 다른 세션이 같은 시각에 같은 이름을 만들 수 있어 조회 결과는 실행 시점에 이미 낡을 수 있습니다. `git checkout -b`가 실패하면 숫자 접미사(`-2`, `-3`, …)를 올려 **성공할 때까지** 재시도하고, 최종적으로 사용한 이름을 결과 보고에 남기세요.

## 결과 보고

다음을 보고하세요:

- 사용된 경로: A(plan 기반) 또는 B(변경사항 기반)
- 대상 텍스트: 테스트 설명 또는 변경 요약
- 분기 기점: 어느 브랜치에서 갈라졌는지 (기본 브랜치가 아니면 그 사실과 사용자가 선택한 결과)
- 생성된 브랜치명

## 하지 말아야 할 것

- 여러 테스트 또는 무관한 여러 변경사항을 한 브랜치에 묶기
- 브랜치명에 한국어나 특수문자 사용하기
- 분기 기점을 확인하지 않고 현재 브랜치 위에 그대로 쌓기 (5단계 2항에서 사용자에게 확인받는다)
- 사용자 확인 없이 기본 브랜치로 checkout 해서 분기 기점을 바꾸기
- 이미 존재하는 브랜치명과 충돌하기 (충돌 시 숫자 접미사 추가)
- `plan.md`가 없고 변경사항도 없을 때 임의로 브랜치 생성하기
- 사용자에게 알리지 않고 `git stash` 등 작업 디렉토리를 변경하는 부수 작업 수행하기
