# 코드 리뷰 기준

언어·프레임워크와 무관하게 코드 리뷰에서 확인할 관점과 지적 작성 형식을 정의한다. `CLAUDE.md`의 TDD·Tidy First·일반 행동 규칙과 스택별 규칙(`backend/`, `frontend/`)을 전제로 하며, 그 규칙들이 다루지 않는 **일반적으로 통용되는 리뷰 관점**(정확성, 보안, 중복, 코드 스멜, 컨벤션, 테스트)만 다룬다.

아키텍처 규칙 위반(계층 의존 방향, CQRS-lite 흐름, Rich Domain, Repository 도구 선택 등)은 이 문서의 대상이 아니다. 그 판정은 `backend/shared/architecture.md`와 각 스택 규칙이 담당하며, 리뷰 시 두 축(스택 규칙 + 이 문서)을 함께 적용한다.

`paths`는 소스·스크립트·인프라 파일을 덮는다. 패턴에 걸리지 않는 파일(문서 등)을 리뷰할 때는 `code-reviewer` 에이전트가 이 파일을 명시적으로 읽어 기준으로 삼는다 — 미매칭이 "이 기준을 적용하지 않는다"는 뜻은 아니다.

## 1. 심각도 등급

모든 지적에 아래 4단계 중 하나를 부여한다. 등급 없이 지적을 나열하지 않는다 — 등급이 없으면 리뷰를 받은 사람이 무엇을 먼저 고쳐야 하는지 알 수 없다.

| 등급 | 정의 | 처리 |
|---|---|---|
| Blocker | 머지하면 장애·데이터 손상·보안 취약점이 발생한다 | 반드시 수정 후 머지 |
| Major | 동작은 하지만 결함 가능성이 높거나 규칙을 위반한다 | 수정 권장, 미수정 시 근거 필요 |
| Minor | 가독성·유지보수성 개선 여지 | 작성자 판단 |
| Nit | 취향에 가까운 사소한 제안 | 작성자 재량. 무시해도 무방하다는 사실은 요약에서 한 번만 밝힌다(11.3절) |

- 확신이 낮은 지적은 등급을 올리지 않고 "확신도 낮음"을 함께 표기한다. 추측을 Blocker로 올리지 않는다.
- 도구(포매터·린터·타입 체커)가 결정적으로 잡아내는 항목은 리뷰 지적으로 중복 나열하지 않고 도구 실행 결과로 대체한다.

## 2. 리뷰 범위

- **변경분(diff)에 집중한다.** 변경된 라인과 그 직접적 맥락(호출부, 영향받는 테스트)만 본다. 변경과 무관한 기존 코드의 문제는 지적하지 않는다(사용자가 명시적으로 요청한 경우는 예외).
- 무관한 기존 문제를 발견하면 지적 목록이 아니라 별도의 "참고" 항목으로 분리해 언급만 한다. 이번 변경의 머지 조건으로 삼지 않는다.
- 변경 규모가 커서 전부 볼 수 없으면, 본 범위와 보지 못한 범위를 명시한다. 전부 본 것처럼 보고하지 않는다.
- 삭제된 코드도 리뷰 대상이다. 삭제로 인해 호출부가 깨지거나 테스트가 사라졌는지 확인한다.

## 3. 정확성

가장 먼저 확인한다. 아래는 실제 결함으로 이어지는 빈도가 높은 지점이다.

- **경계 조건**: 빈 컬렉션·단일 원소·최대치, off-by-one, 인덱스 범위, 빈 문자열과 공백 문자열의 구분.
- **null/부재 표현**: null 반환·전달 경로, Optional/nullable 타입의 부재 처리 누락, null과 "값이 없음"을 다르게 취급해야 하는 경우의 혼동.
- **예외 경로**: 실패 시 상태가 일관되게 남는지(부분 성공으로 데이터가 깨지지 않는지), 롤백 경계가 실제 변경 범위를 덮는지.
- **동시성**: 공유 가변 상태, 검사 후 실행(check-then-act) 경쟁, 트랜잭션 경계 밖의 상태 변경, 원자성이 필요한 연산의 분리 실행.
- **부동소수점·수치**: 금액·수량에 부동소수점 사용, 정수 오버플로, 나눗셈의 0 분모.
- **날짜·시간**: 타임존 누락(로컬 시간 혼용), 서버 시간에 대한 암묵적 의존, 윤년·월말 처리.
- **입력 신뢰**: 외부 경계(HTTP 요청, 메시지, 파일, 외부 API 응답)를 넘어온 값을 검증 없이 신뢰하는 코드.

## 4. 보안

- **주입(injection)**: SQL·NoSQL·셸 명령·LDAP·템플릿을 문자열 연결로 조립하는 코드. 바인드/파라미터화된 방식으로 대체를 요구한다.
- **인증·인가**: 엔드포인트·핸들러에 인가 검사 누락, 리소스 소유자 확인 없이 식별자만으로 접근 허용(IDOR), 클라이언트가 보낸 권한 값을 그대로 신뢰.
- **시크릿**: 코드·설정 파일·테스트에 하드코딩된 키·토큰·비밀번호·커넥션 문자열. 커밋 대상에 `.env`류 파일이 포함됐는지 확인한다.
- **민감정보 노출**: 로그·에러 응답·예외 메시지에 비밀번호·토큰·주민번호·카드번호·전체 요청 본문을 그대로 출력. 스택 트레이스를 클라이언트에 반환.
- **암호화·해시**: 비밀번호를 평문 저장하거나 단순 해시(MD5·SHA-1 단독) 사용, 검증 없이 자체 구현한 암호화, 안전하지 않은 난수(예측 가능한 시드)를 토큰 생성에 사용.
- **역직렬화·파일 처리**: 신뢰할 수 없는 입력의 역직렬화, 사용자 입력을 경로에 결합(path traversal), 업로드 파일의 타입·크기 미검증.
- **전송·설정**: HTTPS 아닌 평문 전송, 인증서 검증 비활성화, CORS `*`와 인증 정보 동시 허용, 디버그 모드·상세 에러 노출 설정이 프로덕션 경로에 포함.
- **의존성**: 새로 추가된 의존성의 알려진 취약점·유지보수 상태·라이선스. 표준 라이브러리로 충분한 기능에 새 의존성을 추가했는지도 확인한다.

## 5. 중복

- **동일 로직 3회 이상 반복**이면 추출을 요구한다(rule of three). 2회는 위치와 변경 이유가 같은 경우에만 추출을 제안한다 — 우연히 닮은 코드를 성급히 합치면 이후 서로 다른 이유로 변경될 때 분리 비용이 더 크다. 이 조항은 `CLAUDE.md` 4번("중복을 철저히 제거")을 리뷰 판정 기준으로 구체화한 것이며, 무엇을 제거 대상으로 지적할지는 이 조항이 정한다.
- **지식의 중복**을 코드의 중복보다 우선해서 본다: 같은 비즈니스 규칙(할인율, 상태 전이 조건, 검증 임계값)이 여러 곳에 각각 구현돼 있으면 한 곳이 바뀔 때 나머지가 남는다.
- 복사-붙여넣기 흔적(주변 변수명만 바뀐 블록, 동일한 주석)을 신호로 삼는다.
- **의도된 중복은 지적하지 않는다.** 다중 진입점 방어를 위한 계층별 검증 중복처럼 규칙이 명시적으로 요구하는 중복은 제거 대상이 아니다(`backend/shared/architecture.md` 5번).

## 6. 코드 스멜과 리팩터링

아래 스멜이 보이면 대응하는 리팩터링을 이름과 함께 제안한다. 이름 없는 "정리하세요"는 지적으로 인정하지 않는다.

| 스멜 | 신호 | 제안할 리팩터링 |
|---|---|---|
| 긴 함수 | 한 함수가 여러 추상화 수준을 섞고, 요약에 "그리고"가 필요하다 | 함수 추출(Extract Function) |
| 긴 파라미터 목록 | 연관된 파라미터가 그룹화 기준을 넘는다 (백엔드는 `backend/shared/architecture.md` 4번의 기준을 따르고, 기준이 없으면 4개 이상) | 파라미터 객체 도입(Introduce Parameter Object) |
| 큰 클래스 | 필드·책임이 여러 축으로 나뉜다 | 클래스 추출(Extract Class) |
| 기능 편애 | 다른 객체의 데이터를 꺼내 계산한다 | 함수 이동(Move Function) |
| 원시값 집착 | 의미 있는 개념을 String·int로 나른다 | 값 객체로 대체(Replace Primitive with Object) |
| 조건문 복잡 | 중첩 if, 반복되는 타입 분기 | 보호 구문(Guard Clause), 다형성으로 조건 대체 |
| 산탄총 수술 | 하나의 변경이 여러 파일에 흩어진 수정을 요구한다 | 함수·필드를 한 모듈로 이동 |
| 죽은 코드 | 호출되지 않는 함수, 항상 참인 조건, 도달 불가 분기 | 제거(단, 이번 변경이 만든 것만 — `CLAUDE.md` 6.3절 외과적 변경) |
| 주석으로 설명하는 코드 | 주석이 코드가 무엇을 하는지 번역한다 | 이름 개선, 함수 추출 |
| 추측성 일반화 | 사용처가 하나인 추상화, 쓰이지 않는 확장 지점 | 제거(YAGNI) |

- 스멜 지적은 **동작 변경 없이 해소 가능한지**를 함께 판단한다. 순수 구조적 변경이면 별도 커밋으로 분리하도록 안내한다(Tidy First).
- 과잉 방어도 스멜로 다룬다: 발생 불가능한 시나리오의 예외 처리, 도달할 수 없는 기본값 분기는 단순화를 제안한다.

## 7. 명명과 코드 컨벤션

- **이름이 의도를 드러내는지** 본다: 무엇을 하는지가 아니라 왜 존재하는지. `data`, `info`, `manager`, `util`, `process`, `handle` 같은 무의미한 이름과 `tmp`, `a1` 같은 축약을 지적한다.
- 불리언은 술어형(`isActive`, `hasPermission`), 컬렉션은 복수형, 함수는 동사구, 클래스는 명사구로 맞춘다.
- **같은 개념에 같은 이름**을 쓰는지 확인한다. 한 코드베이스에서 `fetch`/`get`/`load`, `delete`/`remove`가 뒤섞이면 하나로 통일을 제안한다.
- 표기 관례(파일명, 상수, 패키지·모듈명)는 해당 언어·프레임워크의 커뮤니티 표준을 따르는지 확인한다. 프로젝트 안에 이미 확립된 관례가 있으면 그것이 우선한다.
- 포매팅(들여쓰기, 줄바꿈, import 정렬)은 리뷰에서 손으로 지적하지 않는다. 포매터·린터 설정으로 강제할 대상이며, 설정 자체가 없으면 그것을 지적한다.
- 주석은 "왜"만 남기고 "무엇"은 코드로 표현하도록 요구한다. 변경으로 사실과 어긋나게 된 주석·문서는 Major로 다룬다.

## 8. 에러 처리와 로깅

- 예외를 삼키는 코드(빈 catch, 로그만 남기고 정상 흐름 계속)를 지적한다. 복구할 수 없으면 전파한다.
- 예외 타입이 상황을 구분하는지 확인한다. 모든 실패를 하나의 일반 예외로 뭉개면 호출부가 대응할 수 없다.
- 에러 메시지에 원인 파악에 필요한 맥락(식별자, 입력 값의 범위)이 있는지, 동시에 민감정보가 없는지(4번) 양쪽을 본다.
- 로그 레벨이 적절한지 확인한다: 정상 흐름에 error, 대량 반복 경로에 info 이상, 디버깅 잔여물(`print`, `console.log`, 임시 로그)의 잔존.
- 재시도·타임아웃: 외부 호출에 타임아웃이 없거나, 재시도가 멱등하지 않은 연산에 걸려 있는지 확인한다.

## 9. 성능

측정 없는 최적화 요구는 하지 않는다. 아래처럼 **구조적으로 확정된 문제**만 지적한다.

- 반복문 안의 I/O(쿼리·HTTP 호출) — N+1 패턴.
- 전체 조회 후 애플리케이션에서 필터링·정렬·집계(저장소에서 처리 가능한 경우).
- 페이지네이션 없는 목록 조회, 상한 없는 배치 크기.
- 불필요한 전체 복사(대용량 컬렉션의 반복 복사), 루프 안에서 매번 재생성되는 불변 객체(정규식, 포매터, 설정 객체).
- 락 보유 구간에 I/O 포함, 트랜잭션 안의 외부 API 호출.

## 10. 테스트

- 변경된 동작에 대응하는 테스트가 있는지 확인한다. 결함 수정이면 **그 결함을 재현하는 테스트**가 함께 있는지 본다(`CLAUDE.md` 2.1절).
- 테스트가 구현 세부가 아니라 **관찰 가능한 동작**을 검증하는지 본다. 내부 호출 순서만 검증하는 mock 중심 테스트는 리팩터링을 막는다.
- 어서션이 실제로 의미를 검증하는지 확인한다: 어서션 없는 테스트, "예외가 안 나면 통과"하는 테스트, 항상 참인 어서션.
- 결정성: 시간 대기(`sleep`)로 순서를 보장, 현재 시각·실행 순서·외부 네트워크에 의존, **어서션이** 난수에 의존, 테스트 간 상태 공유. 테스트 데이터 팩토리 도구(Instancio, Polyfactory, Fishery 등)로 검증과 무관한 필드를 랜덤 생성하는 것은 문제가 아니다 — 어서션 대상 필드를 랜덤에 맡기거나 seed 재현 수단 없이 랜덤을 쓰는 경우만 지적한다.
- 경계 조건과 실패 경로에 테스트가 있는지 본다. 정상 경로만 있는 테스트는 Minor 이상으로 다룬다. 같은 로직의 다중 케이스를 테스트 메서드 복사로 나열했다면 parameterized 테스트(`@ParameterizedTest`/`pytest.mark.parametrize`/`test.each`)를 제안한다.
- 커버리지 수치를 목표로 요구하지 않는다. 크리티컬 경로와 엣지 케이스의 존재 여부로 판단한다.

## 11. 지적 작성 형식

**한 줄이 기본이다.** 리뷰는 읽는 사람이 훑어서 무엇을 고칠지 파악하는 문서다. 설명이 길면 읽히지 않는다.

### 11.1. 기본형

등급별 섹션으로 묶고, 각 지적은 `` `파일:라인` 문제 키워드 → 제안 `` 한 줄로 쓴다. 항목마다 등급을 반복하지 않는다.

```
### Major
- `OrderService.java:88` 취소된 주문에 재고가 두 번 복원된다 → 보호 구문(Guard Clause)으로 상태 검사 후 조기 반환
- `PaymentClient.ts:24` 외부 호출에 타임아웃 없음 → 타임아웃과 재시도 상한 지정

### Minor
- `UserFinder.java:31` 목록 조회에 페이지네이션 없음 → size 상한을 둔 페이징 파라미터 추가
```

- **키워드를 앞에 둔다.** 문제의 핵심 명사구로 시작한다. "~하는 것으로 보입니다", "~일 수 있습니다" 같은 완충어와 경위 설명을 붙이지 않는다.
- **`→` 뒤는 조치 한 조각이다.** 리팩터링 이름이나 대체할 값·플래그·명령을 쓴다. "검토가 필요하다"로 끝내지 않는다.
- 코드 근거로 `파일:라인`을 인용한다. 파일명만 쓰지 않는다.
- 사람이 아니라 코드를 지적한다.

### 11.2. 등급별 분량 상한

| 등급 | 상한 | 두 번째 줄 |
|---|---|---|
| Blocker · Major | 최대 2줄 | 실패 시나리오가 한 줄로 담기면 `왜:` 한 줄 추가 허용 |
| Minor · Nit | 1줄 고정 | 붙이지 않는다 |

- `왜:` 줄은 "어떤 입력·상황에서 어떻게 깨지는가"만 쓴다. 규칙 원문 인용, 코드 경위 설명, 대안 비교는 넣지 않는다.
- 상한에 담기지 않는 근거는 본문에서 **분리**해 별도 상세 항목으로 둔다(게시 매체에서의 배치 방법은 커맨드가 정한다). 본문 줄을 늘려 해결하지 않는다.
- Nit이 3건을 넘으면 한 줄에 쉼표로 묶어 나열한다.

### 11.3. 공통

- 지적은 심각도 순으로 정렬한다. 같은 등급 안에서는 파일 순으로 묶는다.
- 문제가 없으면 억지로 지적을 만들지 않고 없다고 보고한다. Nit만 남는 리뷰는 그 사실을 명시한다.
- 요약은 등급별 개수 한 줄로 낸다(`Blocker N / Major N / Minor N / Nit N`). 같은 내용을 산문으로 다시 쓰지 않는다. Nit이 있으면 이 줄이나 맺음말에서 "Nit은 무시해도 무방하다"를 한 번만 밝힌다(1번).

## 12. 금지 패턴

- 심각도 등급 없이 지적을 나열하지 않는다(1번).
- 확신이 낮은 추측을 Blocker/Major로 올리지 않는다(1번).
- 변경분과 무관한 기존 코드를 머지 조건으로 지적하지 않는다(2번).
- 포매터·린터가 결정적으로 잡는 항목을 손으로 나열하지 않는다(1번, 7번).
- 측정 근거 없이 성능 최적화를 요구하지 않는다(9번).
- 리팩터링 이름 없이 "정리하세요"·"개선하세요"로 끝내지 않는다(6번).
- `파일:라인` 근거 없이 지적하지 않는다(11.1절).
- 지적을 산문으로 풀어쓰지 않는다. 등급별 분량 상한(Blocker·Major 2줄, Minor·Nit 1줄)을 넘기지 않는다(11.2절).
- 완충어("~로 보입니다")·경위 설명·규칙 원문 인용으로 줄을 늘리지 않는다(11.1절, 11.2절).
- Minor·Nit에 `왜:` 줄을 붙이지 않는다(11.2절).
- 등급별 개수 요약을 산문으로 중복 서술하지 않는다(11.3절).
- 규칙이 의도적으로 요구하는 중복(계층별 검증 등)을 중복 제거 대상으로 지적하지 않는다(5번).
- 커버리지 수치 목표를 리뷰 조건으로 요구하지 않는다(10번).
