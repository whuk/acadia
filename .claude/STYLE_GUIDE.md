# .claude 문서 스타일 가이드

`.claude/rules/`, `.claude/commands/`, `.claude/agents/`와 `CLAUDE.md`에 적용되는 공통 문서 포맷을 정의한다. 새 문서를 작성하거나 기존 문서를 수정할 때 이 가이드를 따른다.

## 1. 적용 범위와 문서 유형

문서 유형은 4가지로 나뉜다. 유형마다 frontmatter 스키마와 헤딩 표기 방식이 다르지만, "섹션에 정해진 순서가 있고 종결 섹션으로 끝난다"는 원칙(5번)은 공통이다. 헤딩 표기는 유형별로 다음을 따른다: Rule/Meta는 `## N. 제목`(4번), Command는 `## N단계: 제목`(7번), Agent는 순서는 고정하되 번호 없는 `## 제목`(8번) — Agent 문서는 다른 파일이 섹션 번호로 인용할 일이 없는 절차 스크립트이므로 번호를 강제하지 않는다.

| 유형 | 경로 | 용도 |
|---|---|---|
| Rule | `.claude/rules/**/*.md` | 코드 작성 규칙, 조건부 로딩(`paths`) 대상 |
| Command | `.claude/commands/**/*.md` | 슬래시 커맨드 정의 |
| Agent | `.claude/agents/*.md` | 서브에이전트 정의 |
| Meta | `CLAUDE.md`, 이 문서 | frontmatter 없이 Claude에게 지침으로 로드되는 최상위 문서 |

`README.md`는 이 가이드의 적용 대상이 아니다. Claude에게 주는 지침이 아니라 GitHub에서 저장소를 처음 보는 사람에게 보여주는 소개 문서이기 때문에, 번호 매긴 섹션·frontmatter 같은 내부 지침 문서 관행을 강제하지 않고 일반적인 README 관행(뱃지, Quick Start 등)을 자유롭게 따른다. `.claude/statusline.md`도 같은 이유로 적용 대상이 아니다 — Claude에게 로드되는 지침이 아니라 사용자가 참고하는 도구 설정 가이드다.

## 2. 공통 원칙 (4가지 유형 모두)

- **언어**: 설명은 한글로 작성한다. 클래스명·함수명·CLI 플래그 등 코드 식별자는 원문(영문)을 유지한다.
- **톤**: 기술 문서 톤을 유지한다. 이모지를 사용하지 않는다.
- **구조**: 첫 줄은 H1 제목. 그 다음 줄은 반드시 1~3문장의 목적 진술(이 문서가 무엇을 다루는지, 무엇을 전제하는지)이다. 목적 진술 없이 바로 `## 1.`로 들어가지 않는다. 단, Agent 문서는 예외로 H1 없이 `## 역할`부터 시작한다(8번) — frontmatter의 `name`이 제목 역할을 하고, 역할 섹션의 1~2문장이 목적 진술을 겸한다.
- **참조**: 다른 문서를 가리킬 때는 파일명을 인라인 코드로 감싼다 (`` `domain.md` 9번 참조 ``). 상대 경로 전체를 쓰지 않는다. 단, Agent/Command 문서에서 실행 중 실제로 읽어야 할 파일을 지시하는 목록(참조 규칙 등)은 `.claude/`부터의 전체 경로를 허용한다 — 서브에이전트가 경로 그대로 파일을 열 수 있어야 하기 때문이다.
- **최소 충분**: 현재 다루는 규칙/절차에 필요한 내용만 쓴다. 미래에 필요할 수도 있는 조항을 미리 만들지 않는다.

## 3. Frontmatter 스키마

유형별로 다음 필드를 **모두 명시**한다. 해당 사항이 없어도 값을 `없음`으로 명시하고, 필드 자체를 생략하지 않는다 — 생략은 "정의 안 함"과 "값이 없음"을 구분할 수 없게 만든다. 단, `선택`으로 표시한 필드는 이 원칙의 예외이며 해당하지 않으면 필드를 두지 않는다.

### 3.1. Rule

```yaml
---
description: <한 줄 요약>
paths:                            # 선택. 매칭되는 파일을 읽을 때만 로드
  - "<glob 패턴>"
  - "<glob 패턴>"
---
```

- **조건부 로딩 필드의 이름은 `paths`이고 값은 YAML 리스트다.** Cursor 계열의 `globs: "a,b,c"`(쉼표 구분 문자열)나 `alwaysApply: true`는 Claude Code가 인식하지 않는다. 그렇게 쓰면 오류가 나지 않고 **조건부 로딩이 걸리지 않은 채 매 세션 무조건 로드**되므로, 규칙을 스택별로 나눠 둔 의미가 사라진다.
- **항상 로드할 규칙은 `paths` 필드를 두지 않는 것으로 표현한다.** `paths`가 없으면 무조건 로드가 기본 동작이다. "항상 로드"를 뜻하는 별도 필드를 만들지 않는다.

### 3.2. Command

```yaml
---
description: <한 줄 요약>
argument-hint: <입력값 형식 힌트, 인자를 받지 않으면 "없음">
user-invocable: true               # 사용자가 /명령어로 직접 호출 가능하면 true, 항상 명시
allowed-tools: <콤마 구분 목록>     # 선택. 커맨드 실행 시 허용할 도구
disable-model-invocation: true     # 선택. 사용자만 트리거하게 제한할 때
---
```

- 파일 삭제·이동처럼 되돌릴 수 없는 동작을 하는 커맨드는 `allowed-tools`로 필요한 도구만 열어둔다. 그런 동작이 없으면 두 선택 필드를 생략한다.
- 인자 설명은 **frontmatter의 `argument-hint` 한 곳에서만** 한다. 본문 맨 끝에 `$ARGUMENTS - 필수: ...` 같은 줄을 중복 기재하지 않는다.
- 본문에서 인자 값을 설명해야 하면 `## 1단계`(또는 그에 준하는 첫 실행 단계) 안에서 `$ARGUMENTS`를 인라인으로 참조한다.

### 3.3. Agent

```yaml
---
name: <kebab-case 이름>
description: <이 에이전트를 언제 위임하는지, 형제 에이전트와의 구분점 포함>
tools: <콤마 구분 목록>            # 전체 도구 허용 시 생략하지 말고 tools: '*' 로 명시
model: inherit | opus | sonnet | haiku
---
```

- `tools` 필드를 생략해 "전체 허용"을 암묵적으로 표현하지 않는다. `tools: '*'`로 명시한다. 와일드카드는 YAML 앵커 문법과 충돌하지 않도록 작은따옴표로 감싼다.

### 3.4. Meta (CLAUDE.md)

frontmatter를 사용하지 않는다. H1부터 시작한다.

## 4. 헤딩 구조와 넘버링 (Rule, Meta)

이 절은 Rule과 Meta(CLAUDE.md) 문서에 적용된다. Command는 7번의 `## N단계`, Agent는 8번의 번호 없는 고정 순서를 따른다.

- H1(`#`)은 문서당 하나, 제목 전용.
- 최상위 섹션은 `## N. 제목` 형식으로 1부터 순번을 매긴다. 순번 없는 `## 제목`을 최상위 섹션에 섞어 쓰지 않는다. 하위 섹션을 순번 있는 최상위 섹션 안에 넣지 않고 별도 래퍼 H2로 감싸지 않는다.
- 하위 섹션이 필요하면 `### N.M. 제목`으로 부모 섹션 번호를 이어받는다. 하위 섹션 없이 최상위 섹션만으로 충분하면 H3을 만들지 않는다.
- 번호는 파일 전체에서 끊기지 않고 이어진다(중간에 1로 재시작하지 않는다).

## 5. 종결 섹션 (필수, 파일의 가장 마지막)

Rule/Command/Agent 문서는 금지 패턴 섹션으로 끝난다. 다른 섹션 뒤에 부록처럼 덧붙이지 않고 파일의 **가장 마지막 섹션**이어야 한다.

- Rule 문서: `## N. 금지 패턴` (마지막 번호 섹션).
- Command 문서: `## 하지 말아야 할 것` (번호 없음).
- Agent 문서: `## 금지 패턴` 또는 `## 하지 말아야 할 것` 중 하나로 통일해서 쓴다.
- Meta 문서 중 CLAUDE.md에는 이 섹션을 두지 않는다. 이 가이드 자체는 예외로 금지 패턴 섹션(9번)으로 끝난다.
- 특정 도구나 하위 주제에만 국한된 금지 항목은 해당 최상위 섹션의 하위 섹션(`### N.M. 금지 패턴`)으로 둘 수 있다. 이 허용은 하위 섹션에 한정되며, 파일 전체를 다루는 최상위 금지 패턴 섹션은 여전히 가장 마지막에 있어야 한다.

## 6. Rule 문서 전용 규칙

- `spring/`/`nestjs/`/`fastapi/`(백엔드 스택), `java/`/`kotlin/`(언어), `layered/`/`hexagonal/`(아키텍처), `repository.md`·`repository-tools.md`/`repository-sql.md`(영속성 도구), `nextjs.md`/`vite.md`/`vue.md`(프론트 프레임워크)처럼 상호 배타적인 대안이 있는 문서는 목적 진술 바로 다음 문단에 아래 문장을 그대로 사용한다 (배타 축이 여러 개면 각 축마다 같은 형식의 문장을 이어 쓴다):
  > "이 프로젝트가 X를 채택했다면 이 파일은 적용 대상이 아니다. A와 B를 한 프로젝트에서 동시에 쓰지 않으므로, 실제로 채택하지 않은 [프레임워크/아키텍처 스타일]의 규칙 파일은 프로젝트에서 제외한다 (`other.md` 참조)."

## 7. Command 문서 전용 규칙

- 단계는 `## N단계: 제목` 형식으로 통일한다. 헤더 없이 번호 목록만 나열하지 않는다.
- 하나의 단계 안에서 **상호 배타적인 실행 경로**로 분기하면 `### 경로 A: 조건`처럼 레터링한 H3으로 중첩한다. 동시에 여러 개가 적용될 수 있는 **조건 나열**(예: 스택 조합별 처리 목록)은 `### 조건 — 처리` 형식의 서술형 H3을 허용한다.
- 마지막 실행 단계 다음에 "## 결과 보고" 섹션(무엇을 보고할지 목록)을 두고, 그다음 5번의 "하지 말아야 할 것"으로 마무리한다.
- Command의 코드 블록은 참고용 예시가 아니라 **실행 지시**다. 셸 명령은 `bash` 코드 블록으로 제시하고, 실행 시점에 실제 값으로 바꿔야 하는 자리는 `{slug}`, `{일수}`처럼 중괄호로 표기한다. 중괄호가 없는 문자열은 그대로 실행할 리터럴이다.
- 사용자에게 그대로 보여줄 메시지는 `>` 인용문으로 적고, 실행을 멈춰야 하는 지점은 **중단**으로 강조한다.
- 파일 삭제·이동처럼 되돌릴 수 없는 동작은 대상 목록을 먼저 제시하고 사용자 승인을 받은 뒤 실행하도록 단계를 나눈다. 승인 없이 실행하지 않는다는 조항을 "하지 말아야 할 것"에도 함께 적는다.

## 8. Agent 문서 전용 규칙

모든 에이전트 문서는 family(구현체/설계자/검사자/리뷰어 등)와 무관하게 H1 없이 `## 역할`부터 시작하고(2번 구조 예외) 다음 순서를 따른다. 해당 사항이 없는 섹션도 제목만 남기고 "해당 없음"이라고 쓰지 않는다 — 그 에이전트에 정말 필요 없는 섹션이면 통째로 생략한다. 단, "다른 에이전트와의 협업"은 형제 에이전트가 하나라도 있으면 반드시 포함한다.

1. **역할** — 1~2문장.
2. **전제** — 언제 이 에이전트를 쓰지 않는지, 형제 에이전트 포인터.
3. **작업 절차** — 번호 매긴 단계.
4. **참조 규칙** — 읽어야 할 rule 파일 목록.
5. **산출물 형식** — 출력 형태(설계안/리뷰 결과/코드 diff 등).
6. **다른 에이전트와의 협업** — 핸드오프 대상과 조건.
7. **금지 패턴 / 하지 말아야 할 것** (5번).

## 9. 금지 패턴

- Frontmatter 필드를 생략해 암묵적 기본값에 의존하지 않는다(3번). Rule의 `paths`는 `선택`으로 표시된 예외이며, 항상 로드할 규칙은 이 필드를 두지 않는 것으로 표현한다(3.1절).
- Rule의 조건부 로딩을 `globs`(쉼표 구분 문자열)나 `alwaysApply`로 적지 않는다(3.1절). Claude Code가 인식하지 않는 이름이라 조용히 무조건 로드로 떨어진다.
- 순번 없는 최상위 `## 제목`을 순번 있는 섹션과 섞어 쓰지 않는다(4번, Rule/Meta 한정 — Command는 `## N단계`와 `## 결과 보고`를 함께 쓴다).
- 최상위 금지 패턴 섹션을 파일 끝이 아닌 중간에 배치하지 않는다(5번. 특정 도구에 국한된 하위 섹션 수준의 금지 패턴은 예외).
- Command 문서에서 인자 설명을 frontmatter와 본문 두 곳에 중복 기재하지 않는다(3.2절).
- 이 가이드에 없는 새 종결 섹션(예: "버전 정보", "변경 이력", "작성자")을 요청 없이 추가하지 않는다.
