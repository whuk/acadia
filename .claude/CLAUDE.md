# CLAUDE.md

이 저장소에서 코드 작업 시 Claude Code에게 제공되는 가이드입니다.
Kent Beck의 테스트 주도 개발(TDD)과 Tidy First 원칙에 따라 개발을 진행합니다.


## 개발 방법론

### TDD 사이클: Red → Green → Refactor

- 작은 기능 증분을 정의하는 실패 테스트를 먼저 작성하세요
- 동작을 설명하는 의미 있는 테스트 이름을 사용하세요 (예: "shouldSumTwoPositiveNumbers")
- 테스트를 통과시키기에 충분한 최소한의 코드만 작성하세요
- 테스트가 통과한 후에만 리팩터링하세요
- 새로운 기능에 대해 사이클을 반복하세요
- 결함 수정 시: API 수준 실패 테스트 → 문제를 재현하는 최소 테스트 → 두 테스트 모두 통과

### Tidy First: 구조적 변경과 동작 변경의 분리

- **구조적 변경**: 동작을 변경하지 않고 코드를 재배치 (이름 변경, 메서드 추출, 코드 이동)
- **동작 변경**: 실제 기능 추가 또는 수정
- 구조적 변경과 동작 변경을 같은 커밋에 절대 섞지 마세요
- 둘 다 필요한 경우 항상 구조적 변경을 먼저 수행하세요
- 변경 전후로 테스트를 실행하여 구조적 변경이 동작에 영향을 주지 않았는지 검증하세요

## 커밋 규율

- 다음 조건을 모두 만족할 때만 커밋하세요:
    1. 모든 테스트가 통과
    2. 모든 컴파일러/린터 경고가 해결됨
    3. 변경이 하나의 논리적 작업 단위를 나타냄
    4. 커밋 메시지에 구조적 변경인지 동작 변경인지 명확히 기술
- 크고 드문 커밋보다 작고 빈번한 커밋을 사용하세요
- 작업 완료 후 자동으로 커밋하지 마세요. 변경 내용과 결과를 먼저 사용자에게 보고하고, 사용자가 커밋을 요청한 경우에만 커밋하세요

## 코드 품질 기준

- 중복을 철저히 제거하세요
- 이름과 구조를 통해 의도를 명확히 표현하세요
- 의존성을 명시적으로 만드세요
- 메서드를 작게 유지하고 단일 책임에 집중하세요
- 상태와 부수 효과를 최소화하세요
- 가능한 가장 단순한 해결책을 사용하세요
- 클래스 참조 시 FQCN을 본문에 직접 쓰지 말고 반드시 import문으로 추출하세요

## 리팩터링 가이드라인

- 테스트가 통과하는 상태(Green 단계)에서만 리팩터링하세요
- 확립된 리팩터링 패턴을 올바른 이름과 함께 사용하세요
- 한 번에 하나의 리팩터링 변경만 수행하세요
- 각 리팩터링 단계 후 테스트를 실행하세요
- 중복 제거 또는 명확성 향상에 기여하는 리팩터링을 우선시하세요

## 워크플로우

새로운 기능에 접근할 때:

1. 기능의 작은 부분에 대한 간단한 실패 테스트를 작성하세요
2. 통과시키기 위한 최소한의 코드를 구현하세요
3. 테스트를 실행하여 통과를 확인하세요 (Green)
4. 필요한 구조적 변경을 수행하세요 (Tidy First), 각 변경 후 테스트를 실행하세요
5. 구조적 변경을 별도로 커밋하세요
6. 다음 작은 기능 증분에 대한 테스트를 추가하세요
7. 기능이 완성될 때까지 반복하며, 동작 변경과 구조적 변경을 별도로 커밋하세요

## 일반 행동 규칙

LLM이 흔히 범하는 코딩 실수를 줄이기 위한 횡단 규칙입니다. TDD/Tidy First 위에 얹는 행동 가이드이며, 사소한 작업에는 판단에 따라 유연하게 적용합니다.

**트레이드오프:** 이 규칙들은 속도보다 신중함에 무게를 둡니다.

### 1. 코드 작성 전에 생각하라

**가정하지 말라. 혼란을 숨기지 말라. 트레이드오프를 드러내라.**

구현 전에:

- 가정을 명시적으로 진술하세요. 불확실하면 질문하세요.
- 해석이 여러 가지라면 모두 제시하세요. 침묵 속에 임의로 고르지 마세요.
- 더 단순한 접근이 있다면 그렇게 말하세요. 필요하면 이의를 제기하세요.
- 모호한 지점이 있으면 멈추세요. 무엇이 모호한지 명명한 뒤 질문하세요.

### 2. 단순함 우선

**문제를 푸는 최소한의 코드. 투기적인 것은 금지.**

「코드 품질 기준」의 단순성 원칙을 구체화합니다.

- 요청된 범위를 넘는 기능을 추가하지 마세요.
- 단일 사용처용 추상화를 만들지 마세요.
- 요청되지 않은 "유연성"이나 "설정 가능성"을 도입하지 마세요.
- 발생 불가능한 시나리오에 대한 에러 처리를 추가하지 마세요.
- 200줄을 50줄로 줄일 수 있다면 다시 쓰세요.

스스로에게 묻기: "시니어 엔지니어가 이걸 보고 과복잡하다고 말할까?" 그렇다면 단순화하세요.

### 3. 외과적 변경

**필요한 곳만 건드려라. 본인이 만든 흔적만 정리하라.**

기존 코드를 편집할 때:

- 인접한 코드, 주석, 포맷팅을 "개선"하지 마세요.
- 망가지지 않은 것을 리팩터링하지 마세요.
- 본인이 다르게 짜고 싶더라도 기존 스타일을 따르세요.
- 무관한 죽은 코드를 발견하면 언급만 하세요. 삭제하지 마세요.

본인의 변경이 만든 고아만 정리:

- 본인 변경이 사용처 없게 만든 import/변수/함수만 제거하세요.
- 기존부터 있던 죽은 코드는 요청 없이 삭제하지 마세요.

판정 기준: 변경된 모든 줄이 사용자 요청으로 직접 추적되어야 합니다.

### 4. 목표 기반 실행

**성공 기준을 정의하라. 검증될 때까지 반복하라.**

TDD 사이클의 일반화입니다. 비-TDD 작업(설정 변경, 스크립트, 문서 등)에도 적용합니다.

작업을 검증 가능한 목표로 변환:

- "검증 추가" → "유효하지 않은 입력에 대한 테스트를 작성한 뒤 통과시킨다"
- "버그 수정" → "버그를 재현하는 테스트를 작성한 뒤 통과시킨다"
- "X 리팩터링" → "리팩터링 전후로 테스트가 통과하는지 확인한다"

다단계 작업은 간단한 계획을 진술:

```
1. [단계] → 검증: [확인 방법]
2. [단계] → 검증: [확인 방법]
3. [단계] → 검증: [확인 방법]
```

강한 성공 기준은 독립적으로 루프를 돌게 해줍니다. 약한 기준("작동하게 만들어")은 반복적인 명확화를 요구합니다.
